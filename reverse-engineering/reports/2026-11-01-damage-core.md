## 从技能基数到一次真实敌人扣血

下面是函数934内**已追通的一条命中路径**，不是宣称每个技能都共用同一基数。`ability` 是传入能力记录，`definition` 为其开头指针；名称为解释用途。

```text
scaled_spell = definition.f32(48)
scaled_spell *= f32(1.4)
scaled_spell *= ability.f32(12)
scaled_spell *= ability.f32(52)
scaled_spell *= category_scale
hp_component = state.f32(1176) * ability.f32(72)
if not (definition.f32(48) > 0):
    hp_component = 0
base = state.f32(1180) * (scaled_spell + hp_component)

U = (u32(rotl32(s0 + s3, 7) + s0) >> 8) * f32(2^-24)
critical = state.f32(1188) > U
amount = critical ? base * state.f32(1192) : base
call 933(state, target_id, amount, spell_id, flags..., critical, ...)
```

`category_scale` 默认1；当 `((definition.u8(84)-2)&255) <= 6` 时，读取内存1577964的七项 float32 表：`[0.5,0.5,1,1,1,1,0.5]`。类别枚举的完整名称尚未确认。随机数使用主状态1528至1540的四个32位字；比较严格使用 `>`，该处没有额外概率 clamp。

这把能力记录的 **`+12` 倍率**接到了实际伤害入口。后续[能力调查](2026-11-01-abilities.md)又确认1065直接更新实际拥有向量，22136从同一向量读取记录后送入917→934→933，因此已解决本报告最初保留的“可能是升级预览副本”疑点。实际运行效果与完整技能系统仍须另外验证。

所有浮点运算实际使用逐步舍入的 binary32，上述顺序与常量需保留。把这些式子任意交换顺序，或改成 JavaScript/Python 的双精度数学，不能称为逐位等价重建。

## 函数933：加区、阶段系数、特例上限与最小伤害

1. 主状态字节 `+2299` 必须等于1，否则整条路径返回。最终目标查找按64位ID，并排除单位首字段等于1的记录；死亡路径确认这个1是死亡标记。
2. 先求一个**加法累积的乘数 M**。基础1，加上满足条件的物品/属性项；不是把每项分别相乘。
3. 输入 `amount *= M`，然后乘一个目标阶段系数P。
4. 特定目标分支还会应用 `hpm/5` 的上限；该分支也可能因技能类别而直接返回。
5. 最终将 NaN 改成1，再取至少1的伤害，直接从敌人HP减去。

M 中能够交叉命名的项来自主状态 `+1012/+1016` 的8字节记录表（字节tag、float32值）：

| tag | 面板/tooltip 支撑的含义 | 函数933中的条件 |
|---:|---|---|
| 18 | Vs Controlled | 单位的三个控制相关到期字段中至少一个大于当前时钟 |
| 19 | Vs Elites | 单位 `+244 != -1` 或 `+412 == 1` |
| 20 | Execute | **当前HP严格小于 `0.3*hpm`** |
| 21 | Vs Afflicted | 单位 `+240 != 0` |
| 28 | Shielded | 主状态 `+1348 > 0` |

同tag的多个值先以float32相加。M还按顺序加上：`now < unit.f32(148)` 时的 `unit.f32(144)`；优先在 `now < unit.f32(156)` 时取 `unit.f32(152)`，否则在 `now < unit.f32(164)` 时取 `unit.f32(160)`；最后加 `unit.f32(364)`。其精确业务名称未完全确认，因此保留偏移，不强行命名具体技能或减益。

P 的静态分支可以恢复成如下结构；这些时间字段及关联记录的业务名称尚未确定：

```text
P = 1
if unit.i32(244) != -1 or unit.i32(64) != -1:
    if unit.f32(408) > now:
        P = 1.5
    elif unit.f32(404) > now:
        P = 0.25
    elif another_unit has i32(0)==0, i32(40)==2, i64(32)==target_id:
        P = 0.25
```

特殊上限分支要求目标 `u32(+40)==3 && u64(+32)==0`。非零技能ID还会查能力类别；类别不超过11且 `(3340 >> category)&1` 为1时整条函数直接返回。其余允许路径将伤害与 `unit.f32(292)/5` 做 NaN-aware minNum 风格选择；结果等于0时返回。这里不是所有敌人的无条件20%上限，也不是直接用传播NaN的 `f32.min` 替换原有select逻辑。

核心扣血及统计可读结构为：

```text
old_hp = unit.f32(288)
damage = amount_after_modifiers
if isNaN(damage): damage = 1
damage = max(1, damage)
unit.f32(288) = old_hp - damage       # 此处不把结果clamp到0
accounted = f32.min(nonnegative_nonNaN(old_hp), damage)
state.f64(824) += f64(accounted)
# 另更新按技能ID归集的统计记录
```

因此过量伤害可以让原始HP变负，统计累计则截在扣血前的非负生命以内；不能把伤害统计面板的增加值直接当成原始扣血量。

```text
unit.i32(0) = 1
unit.f32(344) = 0
unit.i32(240) = 0
```

这些写入与扣血消费者处于同一函数和有守卫的控制流中，支持“已追到真实扣血后死亡状态转换”的结论。函数后半部还存在触发效果、治疗/吸血、事件队列和三处递归伤害调用；本轮没有把这些分支全部重建成完整技能规则。

## 实际HP怎样变成对象更新包

933没有只改内存后就结束。它将刚写入的HP做非负/非NaN处理、向上取整，再无符号饱和转为32位整数，作为**字段索引22**插入更新字段表。随后：

```text
newHP → nonnegative_nonNaN → f32.ceil → u32
fieldMap[22] = encodedHP
updateBlock = byte(0) + packedGUID(target_id) + encodedFieldMaskAndValues(fieldMap)
packet = { opcode: 169 (0x00A9), payload: u32LE(1) + byte(0) + updateBlock }
push packet descriptor into state+1688/+1692/+1696 queue
```

这里的数值opcode直接来自函数50551的 `i32.const 169; i32.store16 offset=12`，没有借外部协议名称猜测。函数15808按8位存在掩码写出64位ID的非零字节；6565输出掩码字数量、32位掩码字、按字段顺序排列的32位值。仅有字段22时对应一个掩码字，bit22为1。

因此“实际扣血→整数HP→对象更新包→待发送/处理队列”已经静态连通；此处单独不能证明该队列一定传给远端，也不能证明远端应用后的显示结果。传输包装、host/guest分流及接收消费属于联机调查的下一段。辅助函数完整记录绑定额外本地REA Evidence `ev_95bddbf35e7e6a67801cf0eb2eae835d7b15175f340364f65451738d341d37b8`，提供方仍为明确命名的本地扩展。

## 接收端延伸：对象更新解析与字段接收系统

接收侧现在也有可定位的指令链，而不是凭协议名称猜测：

1. 通用解码函数878先计算 `(opcode & 65535) - 58`。opcode169对应初始 `br_table` 的第111项、深度122，跳出最初的 `block @586`；机械匹配该block的结束后，下一段立即调用4642。这个关联已经按真实结构化分支深度复核。
2. 4642读取32位更新块数量与一个字节标志；更新类型0分支按相应 `br_table` 跳出block后调用10095读ID，再调用9772读字段掩码及值。
3. 9772按收到的掩码字数量读取掩码，并按置位字段读取32位值。开头的41只是 `min(41,count)` 的容量预分配，不是线上协议的固定掩码上限。
4. 字段读取函数65528/65110明确测试掩码的第22位（字节2的 `0x40`），再从值数组指针 `+88`（`22*4`）取出32位值。65110还返回字段可用性信息；不能简单当成只有一个数值的返回函数。

## 玩家受到伤害：1107

这一方向是独立路径，不能套用敌人最少1点伤害的规则。主状态 `+2299 != 1`、保护标志和某类尚未到期的增益会使其返回。对有限、非负的常规输入，已恢复的主干为：

```text
amount = incoming_amount
if mode_byte_2294 == 1:
    amount *= observed_mode_scaling     # 由原始模式/等级字段计算，完整名称未恢复
amount *= 1 - state.f32(1208)            # arm减伤
if the nearby-unit condition is met:
    amount *= 1 - state.f32(1260)        # 距离平方<=64；只应用一次
if state.f32(1348) > 0:
    absorbed = minNum_like(state.f32(1348), amount)
    state.f32(1348) -= absorbed
    amount -= absorbed
state.f32(1344) -= amount
state.f64(832) += f64(amount)
```

其中模式系数可以按原始偏移恢复为有序结构；各字段和辅助函数38110的完整业务名称未确认，所以不擅自命名难度或等级：

```text
if state.u8(2294) == 1:
    a = state.u32(1888) != 0 ? f32(0.8) : f32(1)
    b = call38110(state.u32(184), state.u32(188)) <u 3 ? f32(0.7) : f32(1)
    n = f32.convert_u32(wrapping_sub_u32(state.u32(2252), 1))
    t = b * n
    t *= f32(0.064)
    t += f32(1)
    t = a * t
    amount = amount * t
```

`wrapping_sub_u32` 保留原始32位减法后再无符号转浮点的顺序；不能把可能为0的字段改作有符号负数计算。吸收消耗还会维护盾来源和触发事件；这些副作用可能在最终扣血前更新其他状态，所以式中的HP是写入时重新读取的当前值。

玩家HP不大于0后存在多种保护/复活分支。已确认其中“剩余生命 `+1440 > 0`”分支减1并将当前HP恢复为生命属性1176的一半；没有剩余生命且前置复活分支未接管时，将HP写0并调用7654，后者把运行状态字节2299写为4。其余特定能力/天赋的复活条件尚未完整命名。
